# URBAN SIM 基本構想書とシステム基本設計書

*文書バージョン Ver0.1　改訂日 2026年9月22日*

> URBAN SIM は WORLD SIM のフェーズ01である。本書は URBAN SIM の基本構想と
> システム基本設計をまとめたもので、WorldSim 全体の構想ノート（旧
> `vision.md`。[`../archive/vision.md`](../archive/vision.md) に保管）の
> 考え方を統合し、URBAN SIM として最初に作る範囲を具体化する。文書の Ver0.1
> と、製品の MVP Ver0.1 は別の版管理とする。本書は基本構想と設計方針を
> まとめるものであり、機能の実装完了を示すものではない。
>
> WorldSim は、ひとつの敷地・街区について、①SiteInfo（敷地に関する事実の
> 確認）→ ②法規・建築のシミュレーション（MVE による最大ボリューム、斜線・
> 日影・天空率の検証）→ ③市場・収支のシミュレーション（用途構成ごとの事業
> 収支比較）→ ④プレゼンテーション（再開発後の街の姿と体験を提示）という順で
> 検討を進める一貫した構想である。①②③は本書の第2章（HBUの比較フロー）〜
> 第10章、④は第11章（Presentation Twin）に対応する。数字の最適解を出す
> だけでなく、その建物が実際に建った街の空気感まで見せるところまでを
> WorldSim の範囲と考える。

## この構想で実現すること

WORLD SIMは、不動産開発・不動産経営について、現実のデータを基に複数の計画を比較し、人間の意思決定を支援する統合AIシステムである。

「この土地を、どう利用すれば最も合理的か」という問いに対し、建築・都市計画・市場・鑑定・税務・財務・経営の分析をつなぐ。条件を変えた場合の建築可能量、事業性、将来価値、リスクを繰り返し検討できる仕組みを目指す。

## 最初に実現する範囲

住所と敷地面積を入力し、主要な規制、概算の建築可能量、用途候補、簡易的な事業性を一つの画面で確認できる試作版をつくる。入口となる機能は、最有効使用を検討するHBUアナライザーとする。

## 全体を貫く原則

専門AIが情報の読解と分析を担い、数値は計算プログラムで算定する。重要な結果には出典・日付・計算式・前提を付け、最終的な判断は人間が行う。

## 正確性の層と表現の層を分ける

もう一つの重要な原則は、**正確性の層と表現の層を分離する**ことである。

| 層 | 役割 | 担うもの |
|---|---|---|
| 正確性の層 | 寸法・法規・面積・収支を満たす設計データ | SiteInfo、法規、FreeCAD、MVE、ルールエンジン、収支計算 |
| 表現の層 | 景観・素材・照明・雰囲気の可視化 | Blender、画像生成AI、画像・映像・3D生成 |

- 表現の層は正確性の層を**動かさない**。画像生成で得た形をそのまま建築的に正しいものとして扱わない。
- 画像は「構想案」、FreeCADモデルなど正確性の層のデータは「寸法・法規を満たす設計データ」として明確に区別する。
- 最後にルールエンジンや専門AIで細部を照合し、「きれいだが建築できないイメージ」になることを防ぐ。

この層分けは第11章の Presentation Twin（計画と数値の層／景観と表現の層）に引き継がれる。

## 第1章 基本構想と専門領域

不動産の判断では、一つの条件変更が他の専門領域にも影響する。例えば用途を住宅からホテルに変えると、建築計画だけでなく、建築費、需要、運営費、資金調達条件も変わる。WORLD SIMは、これらを同じ案件と前提条件のもとで比較できるようにする。

### 専門領域ごとに答える問い

| **専門領域** | **中心となる問い** | **主な分析対象** |
|---|---|---|
| 建築と都市計画 | 何を、どれだけ建てられるか | 用途地域、建ぺい率、容積率、道路、接道、斜線、日影、防火、高さ、条例 |
| 再開発と都市開発 | どの制度や事業手法を検討できるか | 市街地再開発、権利変換、共同化、高度利用地区、総合設計、再開発等促進区 |
| 不動産鑑定 | 土地や建物にどの程度の価値があるか | 取引事例比較、収益還元、原価、DCF、開発法 |
| 税務 | 税金を考慮すると、いくら残るか | 法人税、所得税、消費税、固定資産税・都市計画税、取得・登記・譲渡・相続・贈与 |
| 会計と財務 | 投資や資金計画として成立するか | PL、BS、CF、NPV、IRR、ROIC、借入、資本構成、資金調達 |
| 不動産経営 | 保有と運営によって将来どう変わるか | 賃料、稼働率、運営費、修繕、CAPEX、NOI、保有期間、売却価格 |

### 人間とシステムの役割

専門家の知識と判断の手順を、相互に連動する専門AIとして組み込む。システムは選択肢と根拠を提示し、人間が前提を確認して意思決定する。専門家による確認が必要な事項は、確認事項として残す。

### 構想の成熟度を区別する

名称の統一は確定事項とする。技術構成や運用方法は設計案として扱い、データ取得範囲や処理時間は要検証とする。3D都市シミュレーションと現実世界との継続同期は将来構想として段階的に進める。

## 第2章 HBUによる用途の比較

HBUはHighest and Best Useの略で、最有効使用を意味する。建てられる量だけで結論を出さず、法的・物理的な実現可能性、市場性、経済合理性、財務、税務、リスクを合わせて用途候補を比較する。

### 入力から比較までの流れ

| **段階** | **処理** | **取得または整理する内容** |
|---|---|---|
| 1 | 位置を特定 | 住所、地番、緯度経度から対象地を確認する。 |
| 2 | 敷地情報を整理 | 面積、形状、接道、道路幅員、方位、高低差を整理する。 |
| 3 | 都市計画を確認 | 用途地域、指定建ぺい率・容積率、高度地区、防火地域、地区計画などを確認する。 |
| 4 | 建築規制を解析 | 道路による容積率制限、斜線、日影、高さ、接道、条例などを検討する。 |
| 5 | 建築可能量を算定 | 建築面積、延床面積、階数、高さ、各階床面積を条件付きで算定する。 |
| 6 | 用途候補を生成 | 住宅、賃貸・分譲マンション、ホテル、オフィス、商業、複合用途などを挙げる。 |
| 7 | 市場性を分析 | 周辺価格、賃料、需要、競合などを確認する。 |
| 8 | 事業収支を試算 | 建築・開発費と収入、運営費、資金条件を整理する。 |
| 9 | 不動産価値を推定 | 用途と計画条件に応じて評価手法を選び、価値を試算する。 |
| 10 | HBU候補を比較 | 収益性、実現可能性、リスクと根拠を並べて判断材料を示す。 |

### 比較する条件の例

住宅とホテル、賃貸と分譲、利用できる容積率、建築費の上昇、賃料の下落、金利、5年・10年・20年の保有期間などを変更して再計算する。規制変更や制度利用は、適用が確認された条件と仮定の条件を分けて扱う。

HBUの結果は、鑑定・事業収支・税務・金融・経営シミュレーションへ引き渡す。条件が変わった場合は、影響する分析と計算をやり直す。

## 第3章 システム全体の構成

WORLD SIMは、データ基盤、専門AI、計算プログラム、シミュレーション機能、統合制御機能を組み合わせて構築する。担当を分けることで、分析結果の根拠と計算過程を確認できる構成にする。

| **構成要素** | **担当する役割** | **主な入出力** |
|---|---|---|
| 利用画面　UI | 入力、結果の確認、条件変更、比較を行う。 | 住所・敷地、開発目的、投資条件、保有物件。地図、3D、ダッシュボード、チャット、比較、レポート。 |
| 統合制御<br>オーケストレーター | 案件に必要な処理を選び、順序と結果を管理する。 | 案件理解、専門AIの選択、データ取得、分析依頼、計算実行、相互検証、統合結果。 |
| 専門AI | 資料を読み、専門領域ごとに条件と判断材料を整理する。 | 都市計画、法規、計画、再開発、鑑定、市場、コスト、税務、会計、金融、経営、リスク。 |
| 計算エンジン | 同じ入力には同じ手順で数値を計算する。 | 面積、容積、建築費、賃料、NOI、DCF、NPV、IRR、税金、返済、売却価格。 |
| シミュレーション | 用途や条件の異なる計画を比較する。 | 複数シナリオ、感応度分析、収益性とリスクの比較。 |
| データ基盤 | 外部情報を整理し、共通の形式で保存する。 | 行政、都市計画、地図、3D、価格、賃料、人口、建築費、金利、税制、災害、交通。 |
| 根拠管理<br>Evidence Layer | 重要な結果の根拠を各処理にひも付ける。 | 出典、取得日、適用日、前提、計算式、信頼度。 |

### AIと計算プログラムを分ける

AIは法令や行政資料から適用条件を読み取り、根拠と未確認事項を整理する。計算プログラムは、確認した入力と規則を使って数値を算定する。AIによる解釈は、根拠確認を経て計算条件に反映する。

例として、1,000㎡ × 400％ = 4,000㎡という算術は計算プログラムで処理する。この数値だけで実際の最大延床面積を確定せず、他の規制、面積の定義、前提条件を合わせて確認する。

## 第4章 専門AIの役割

専門AIは12の担当に分ける。各担当は、分析結果に加えて、根拠と前提、確認が必要な点を共通形式で返す。以下の名称は機能上の担当を表し、個別のAI製品名ではない。

| **ID** | **専門AI** | **担当する内容と成果** |
|---|---|---|
| A01 | 都市計画AI | 都市計画区域、用途地域、地区計画、高度地区、高度利用地区、特定街区、都市再生特別地区、再開発等促進区などを整理する。<br>出力名：PlanningResult |
| A02 | 建築法規AI | 建ぺい率、容積率、前面道路・道路幅員、接道、斜線、日影、防火・準防火、高さ、条例などを整理する。<br>出力名：BuildingRegulationResult |
| A03 | 建築計画AI | 規制条件を踏まえ、住宅、オフィス、ホテル、商業、物流、複合用途の計画を検討する。階数、延床・専有面積、共用部、駐車場、レンタブル比を整理する。 |
| A04 | 再開発AI | 高度利用地区、総合設計、再開発等促進区、市街地再開発、共同化、権利変換などを検討する。現状規制での可能性と、制度利用を前提にした可能性を分けて示す。 |
| A05 | 不動産鑑定AI | 取引事例比較法、収益還元法、DCF法、原価法、開発法などにより、土地・建物・開発事業の価値を推定する。評価に用いる条件を明示する。 |
| A06 | 市場分析AI | 売買価格、賃料、空室率、競合物件、新築供給、人口、世帯、商圏、交通などを分析し、用途ごとの市場条件を整理する。 |
| A07 | 建築コストAI | 用途、構造、規模、地域から、本体工事、設備、外構、設計監理、解体、造成、各種負担金、予備費を推定する。概算の条件と費目を明示する。 |
| A08 | 税務AI | 取得、建築、保有、賃貸、売却、相続の各段階で税務の影響を整理する。税率・制度には適用年度、根拠、前提条件を必ず保持する。 |
| A09 | 会計と事業収支AI | PL、BS、CFを組み立て、NOI、EBITDA、NPV、IRR、ROICなどを計算エンジンと連携して算定する。収入・費用・投資時期を整理する。 |
| A10 | 金融AI | LTV、DSCR、金利、返済期間、元利均等・元金均等返済、リファイナンスなどを検討し、資金調達と返済のシナリオを比較する。 |
| A11 | 不動産経営AI | 開発後の賃料、稼働率、管理費、修繕費、CAPEX、NOIを整理し、長期保有と売却のシミュレーションにつなげる。 |
| A12 | リスクAI | 建築費上昇、金利上昇、工期遅延、賃料下落、販売価格下落、稼働率低下、売却時の還元利回り上昇などによる変化を検証する。 |

### 分析結果をつなぐ考え方

都市計画AIと建築法規AIが計画条件を整理し、建築計画AIが用途別の計画へつなげる。再開発AIは制度利用による別案を検討し、市場分析AIと不動産鑑定AIが需要と価値の判断材料を加える。

制度の利用可否や規制の適用を未確認のまま確定扱いにしない。異なる資料の内容が食い違う場合は、その不一致を結果とともに示す。

### 収支とリスクの比較

計画案ごとに、開発費、運営収支、不動産価値、資金調達、税務の前提をそろえて比較する。リスクAIは、その前提を変更したときに、どの結果がどの程度変わるかを確認する。

### 共通の責任範囲

専門AIは、資料の読解、条件の整理、シナリオ案の作成、結果の説明を担う。数値の算定は計算エンジンへ渡す。必要な根拠が不足する場合は、無理に一つの結論へまとめず、不足情報と確認事項を出力する。

A03以降の個別出力名や詳細なデータ形式は、共通出力仕様を踏まえて詳細設計で定義する。

## 第5章 データ基盤と根拠の管理

外部データは共通の取得窓口であるData Gatewayを経由させる。表記・単位・位置情報などを整理し、出典、取得日時、信頼度とともにデータベースへ保存する。

### データ取得の流れ

外部データ取得 → 共通形式への整理 → 出典と取得日時の記録 → 信頼度の評価 → データベース保存 → 専門AIと計算エンジンで利用

| **データ区分** | **候補となる取得元や情報** | **主な用途** |
|---|---|---|
| 行政と都市計画 | 国土交通省、自治体オープンデータ、自治体都市計画GIS、国土数値情報など | 都市計画の指定、制度、規制の確認 |
| 地理と周辺環境 | 国土地理院など。緯度経度、地形、標高、道路、鉄道、駅、バス、学校、病院、商業施設、公園 | 位置と敷地条件、交通利便性、周辺環境の分析 |
| 不動産市場 | 不動産情報ライブラリ、地価公示、都道府県地価調査、取引価格、賃料、売買価格、空室、競合 | 用途比較、収支条件、価値の推定 |
| 人口と統計 | e-Stat、自治体統計など。人口、世帯、商圏 | 需要や市場性の分析 |
| 都市の3D情報 | PLATEAUなど。建物形状、高さ、道路、街区 | 3D表示、都市シミュレーション、将来のデジタルツイン |
| 事業と民間情報 | 建築費、金利、税制、災害情報。地図、口コミ、店舗、交通、画像、動画、ニュース | 事業費・リスクの分析、周辺情報や表現の補完 |

取得元は候補であり、APIの有無、対象地域、更新頻度、利用規約、ライセンス、費用、再利用条件を確認して採用する。取得できない情報を自動取得済みとして扱わない。

### 重要な数値から根拠をたどれるようにする

結果の値、情報源、日付、計算式、仮定、信頼度を一組で保存する。都市計画、建築法規、税務、鑑定、市場価格では、この追跡可能性を必須とする。

## 第6章 専門AIの共通出力仕様

専門AIは、人間向けの説明文とともに、他の専門AIや計算エンジンが利用できる構造化データを返す。項目名をそろえることで、結果の受け渡しと根拠確認を行いやすくする。

| **項目名** | **意味** | **記録する内容** |
|---|---|---|
| value | 結果または取得した値 | 例：容積率400％。対象と単位を明確にする。 |
| source | 出典の名称 | 行政資料名、データセット名など。 |
| source_url | 出典の参照先 | 元資料を確認できるURLなど。 |
| retrieved_at | 取得日時 | 情報を取得した日時。 |
| effective_date | 適用日 | 規制や制度などが適用される日。 |
| confidence | 信頼度の指標 | 評価値と、その評価方法。数値だけで正しさを保証しない。 |
| assumptions | 前提条件 | 入力上の仮定、計算に使った条件など。 |
| warnings | 注意と未確認事項 | 欠落情報、資料間の不一致、確認が必要な条件など。 |

この項目名は SiteInfo の [`site_field_provenance`](siteinfo_db_design.md) と同じ考え方（出典・取得日・確認状態を値にひも付ける）にそろえている。

### 出力例の読み方

容積率の値が400％であっても、出典・適用日・対象地が確認できなければ、その土地の確定条件にはできない。信頼度の例示値0.98についても、正解確率98％を意味するかどうかは、評価方法を定めるまで確定しない。

### 詳細設計で補う項目

設計上の補足案として、値の単位、対象地や案件の識別子、確認状態、計算式と計算バージョンの保持方法を定める。根拠が不足する場合は「未確定」を表す状態を用意する。内部値としてUNDETERMINEDを使うかどうかは詳細設計で確定する。

### 条件を変えて再計算する循環

現実のデータ → 専門AIの分析 → 計算 → シミュレーション → シナリオ比較 → 人間の判断 → 条件変更 → 再計算、という循環を基本とする。再計算の結果にも、そのときの前提と根拠を残す。

## 第7章 初期試作版の範囲

MVPは、最初に価値を確認するための最小限の試作版を意味する。初期目標は「住所を入れると、その土地の基本的な開発可能性と簡易事業性が分かる」こととする。

| **区分** | **MVP Ver0.1で目指す内容** | **留意点** |
|---|---|---|
| 入力 | 住所、敷地面積 | 取得できる情報と利用者が補う情報を区別する。 |
| 情報取得 | 緯度経度、用途地域、建ぺい率、容積率、防火指定、高度地区、地区計画、道路 | 自動取得は目標。対象地域と取得方法の検証が必要。 |
| 建築量と費用 | 概算の建築面積、延床面積、有効面積、建築費 | 確認済みの規制と仮定を区別し、概算の範囲を示す。 |
| 市場 | 周辺地価、取引価格、概算賃料 | 出典、時点、比較条件を表示する。 |
| 事業性 | 年間賃料、NOI、開発費、収益価格、簡易IRR | IRRには投資額、時期、保有期間、売却条件などが必要。 |
| 表示と比較 | 主要結果の一覧、用途候補、条件変更による再計算 | 一つの画面で前提と結果を確認できるようにする。 |

### 初期実装から外す範囲

完全な建築自動設計、全国すべての条例の自動解析、完全な税務判断、高度な権利変換、精密な鑑定評価、全国の市場価格予測は、最初の試作版では扱わない。

### 最初につなぐ処理

住所 → 法規 → 建築可能量 → 市場 → 簡易事業収支、という一連の処理を優先する。初期の対象地域、用途、必要な入力項目は実装着手前に定める。

開発ロードマップでは、第1段階で法規と建築可能量をつなぎ、第2段階で市場と簡易収支を加える。MVPの簡易IRRと、第3段階で行う本格的な投資分析は、精度と範囲を分けて設計する。

## 第8章 結果画面と条件変更

ダッシュボードでは、敷地、規制、建築量、用途、収支、価値、リスクを同じ案件として確認できるようにする。以下は画面に載せる情報の例であり、実在の案件の分析結果ではない。

| **表示区分** | **表示する項目** | **表示例または扱い** |
|---|---|---|
| 所在地 | 住所と位置 | 東京都○○区○○。地図上で対象地を確認する。 |
| 敷地 | 面積、形状、道路条件 | 敷地面積1,000㎡という仮想例。 |
| 都市計画 | 用途地域、建ぺい率、容積率など | 建ぺい率80％、容積率400％という仮想例。出典と確認状態を添える。 |
| 建築可能量 | 建築面積、延床面積など | 単純な率の掛け算と、規制を反映した算定結果を区別する。 |
| 用途候補 | 比較対象となる開発案 | 賃貸住宅、ホテル、オフィスなど。 |
| 事業収支 | 総事業費、NOI、IRRなど | 計算条件がそろった項目を表示する。未入力の前提を明示する。 |
| 不動産価値 | 概算の収益価格など | 評価方法、保有期間、売却条件とともに表示する。 |
| リスク | 条件変更に対する結果の変化 | 建築費、金利、賃料などの変化による影響を比較する。 |

### 利用者が試す条件変更の例

| **変更する条件** | **比較する内容** |
|---|---|
| 建築費が10％または15％上昇 | 総事業費、資金需要、収益性への影響 |
| 金利が上昇 | 返済額、資金繰り、投資指標への影響 |
| 賃料が10％下落 | 運営収益、不動産価値への影響 |
| 用途や保有期間を変更 | 住宅とホテル、賃貸と分譲、5年・10年・20年の比較 |

金利の「1％上昇」は、相対的に1％増やす意味か、1パーセントポイント上げる意味かを入力時に明示する。表示速度の目標は数十秒程度とし、実測により検証する。

### AIとツールの役割分担（使用感に基づく補足）

FreeCAD と Blender を比較した使用感として、ひとつの AI に全部を任せるより、得意分野で分担するほうが強い、という判断がある。上表の技術候補を選ぶときの参考にする。

| 担当 | 得意なこと |
|---|---|
| GPT-6 ＋ image2.5 | 空間全体の構想、形態、素材感、光、周辺環境を含む「雰囲気」の表現 |
| Fable（Claude） | 寸法、納まり、部材関係など細部の正確さ |
| FreeCAD | 寸法・法規・パラメータに基づく正確なモデル |
| Blender | 質感、照明、街並み、プレゼンテーション表現 |

雰囲気の表現力は GPT-6＋image2.5 が圧倒的に優れる一方、細かい部分は間違いが多く、細部の正確さでは Fable が優位、という評価である。「正確性の層と表現の層を分ける」原則は、この使い分けに基づく。

### AIサービスを切り替えられる構成

WORLD SIMと各AIサービスの間に、接続をまとめるAI Gatewayを置く構成を検討する。特定のAIベンダーへの依存を抑え、共通の入力と出力で接続できるようにする。

### 開発を分担するときの共通ルール

ChatGPT、Codex、Claude／Claude Code、Geminiなどで開発を分担する場合も、本書を上位の構想として共有する。基本思想、データ定義、計算ロジック、API仕様、検証方法を共通化し、成果物を引き継げるようにする。

製品内で動く12の専門AIと、開発作業を担当するAIサービスは別の役割である。担当するサービスを変更しても、設計とデータの定義が引き継がれる形を目指す。

このリポジトリでは、各ツールへの案内を [`../../CLAUDE.md`](../../CLAUDE.md)（`AGENTS.md`・`GEMINI.md` も同じ内容）にまとめている。

## 第11章 将来の可視化と次の設計

将来は、土地・都市のデジタルツイン、専門AI、不動産データ、建築と金融・経済のシミュレーションを統合する。現実の土地・建物・都市をデジタル空間上に再現し、法律、市場、人口、経済、金融、税制などの条件を変えて将来を比較する。

### 計算結果と計画後の姿を結び付ける

再開発の最終段階では、事業収支や建築ボリュームと連動した画像、映像、3D空間を用い、投資家、地権者、行政、地域住民など相手に応じて計画を伝える。仮称をPresentation Twinとする。

| **層** | **管理する内容** | **利用を検討する手段** |
|---|---|---|
| 計画と数値の層 | SiteInfo、法規条件、面積、寸法、建築量、収支と根拠 | データ基盤、計算・ルールエンジン、FreeCADなど |
| 景観と表現の層 | 建物の見え方、素材、照明、街路、広場、緑地、雰囲気 | Blender、画像生成AI、画像・映像・3D表示など |

表現のために、確定した面積や寸法などを勝手に変えない。生成画像は構想表現として扱い、実際に建築できるかどうかは、規制・寸法・計算の確認によって判断する。

ホテル中心案、オフィス・商業複合案、住宅中心案、広場・緑地重視案を比較し、昼夜、季節、人の流れの違いも伝えられるようにする。ホテル案ならホテルらしい体験価値、住宅案なら暮らし方、再開発案なら広場や街路の空気感まで、案ごとに比較できることを目指す。

## 付録　主な用語

本書で使う略語と技術用語を、読み進めるための簡潔な説明としてまとめる。計算方法や項目の厳密な定義は、個別の設計書で定める。

| **用語** | **本書での意味** |
|---|---|
| HBU | Highest and Best Use。複数の条件を踏まえて検討する最有効使用。 |
| MVP | 価値と実現可能性を確認するための最小限の試作版。 |
| SiteInfo | 位置、面積、形状、道路など、対象地の情報を扱うデータのまとまり。 |
| GIS と PostGIS | GISは地理情報を扱う仕組み。PostGISはPostgreSQLで空間データを扱うための拡張。 |
| API と Gateway | APIはシステム間の接続窓口。Gatewayは複数の接続をまとめて管理する窓口。 |
| オーケストレーター | 専門AIや計算処理を、案件に応じた順序で動かす統合制御機能。 |
| PL　BS　CF | PLは損益計算書、BSは貸借対照表、CFはキャッシュフロー。 |
| NOI | 不動産の運営収入から運営費用を差し引いた純営業収益。 |
| EBITDA | 利払い・税金・減価償却などの影響を除いて営業上の収益力を見る指標。 |
| DCF と NPV | DCFは将来のキャッシュフローを現在価値に換算する方法。NPVは投資を含めた正味現在価値。 |
| IRR と ROIC | IRRは内部収益率。ROICは投下資本に対する利益の水準を表す指標。 |
| LTV と DSCR | LTVは資産価値に対する借入額の比率。DSCRは返済原資が元利返済額をどの程度カバーするかを示す指標。 |
| CAPEX | 建物や設備などに対する資本的な支出。 |
| AM と PM | AMは資産運用の管理、PMは物件の運営管理を指す。 |
| レンタブル比 | 延床面積などに対する賃貸可能面積の割合。面積の定義をそろえて用いる。 |
| Exit Cap Rate | 売却時の価値を推定する際に用いる還元利回り。 |
| 感応度分析 | 前提を変えたとき、結果がどの程度変わるかを調べること。 |
| Evidence Layer | 結果から出典、日時、前提、計算過程をたどるための根拠管理機能。 |
| デジタルツイン | 現実の対象をデジタル空間に再現し、データの更新に合わせて状態を反映する仕組み。 |

# 最大ボリューム探索アルゴリズムの考え方

`envelope.py` の `compute_max_envelope` は次の順に計算します。

## 1. 斜線制限のみによるベースライン（適合建築物）

各規制対象境界線（道路・隣地・北側）からの距離に応じた高さ制限を、敷地全体に
対して「積み上げブロック」として離散化します（`reference_building_blocks`）。
これは天空率比較における法的な比較対象（適合建築物 Pr）そのものであり、
建蔽率は考慮しません（法令上もこの比較用途では敷地全体を使います）。

## 2. 天空率による「ポディウム＋タワー」探索

素朴に「全体を一律に高くする」「勾配を一律に急にする」という探索を最初に
試しましたが、いずれも失敗します。理由は、ベースライン自体が**あらゆる地点で
既に法的な最大高さに達している**ため、どの地点でも一律に大きく／高くした
候補は、ベースラインの**真の上位集合（superset）**になってしまい、
天空率比較（Ps ≧ Pr）を必ず下回るからです（遮る空の面積は高さについて
単調増加のため）。

天空率で実際にボリュームを増やすには、**どこかで我慢して、別の場所で
得をする**トレードオフが必要です。このツールでは以下の単純な家族
（1パラメータ探索×分割高さの小さなグリッド）を採用しています：

1. 分割高さ `H_split`（ベースライン最大高さの30%～70%の候補から選択）を決め、
   `H_split` 以下はベースラインのブロックをそのまま採用（＝境界線上で
   セットバックゼロの壁がある場合でも、その部分は一切変更しないため、
   天空率計算が不安定になる「距離ゼロ・僅かな高さ増分」問題を回避できます）。
2. `H_split` における適合建築物の水平投影形状を「タワー」の平面形状として
   固定し、そこから真上に伸ばせる高さ `extra_h` を、Ps ≧ Pr を満たす範囲で
   二分探索します。
3. 上記を複数の `H_split` 候補で試し、体積が最大になる組み合わせを採用します。

これは**大域最適解ではありません**。実務の設計者であれば、タワー部分を
さらにセットバックして更に高くする、方位によって階段状に絞る、複数の
タワーに分割するなど、より複雑な形状でさらに大きなボリュームを見つけられる
可能性があります。本ツールは「単純だが確実に合法かつ改善余地のある候補」を
自動生成するものと理解してください。

## 3. 建蔽率・容積率の適用

タワー探索後の形状に対し、建蔽率を超える場合は全レイヤーを同じ距離だけ
一律に内側へ侵食（erosion）し、容積率を超える場合は上位階から切り詰めます。

## 4. 日影規制のフィードバック

日影規制のパラメータが指定された場合、最終形状の日影時間を計算し、
違反があれば建物高さ全体を（接地面から）一律スケールダウンする二分探索で
適合させます。これは「どの部分が原因か」を区別しない粗い手法であり、
実際にはタワー部分だけを北側から遠ざける・低くするなど、より的確な
対応で体積を残せる可能性があります。

### 判断の記録

以下は基本設計書に明示がない、または書きぶりと現物がずれていた点について
実装側で下した判断です。**違うと思ったら差し替えてください。**

#### 1. DXF のレイヤ名 — Phase 0 では `MVE-*` を維持、2026-08-30 に `MVCE-*` へ変更

Phase 0 の時点では `MVE-SITE` などの既存レイヤ名をそのまま残しました。
受入基準が「挙動の変更ゼロ」であり、レイヤ名は JW-CAD 側のテンプレート・
線色設定・図面レイヤ分けが依存する出力仕様だからです。

**2026-08-30、直樹の判断で `MVCE-*` に切り替えました。** 基本設計書 7.1 が
`MVCE-ISOCHRONE-{時間}` と書いているのに合わせた形です。

| 旧 | 新 |
|---|---|
| `MVE-SITE` / `MVE-ROAD` / `MVE-SETBACK` / `MVE-OUTLINE` | `MVCE-SITE` / `MVCE-ROAD` / `MVCE-SETBACK` / `MVCE-OUTLINE` |
| `MVE-MESH` / `MVE-FLOORS` / `MVE-PLAN-n` | `MVCE-MESH` / `MVCE-FLOORS` / `MVCE-PLAN-n` |
| `MVE-SHADOW-5M` / `MVE-SHADOW-10M` / `MVE-ISOCHRONE-{時間}H` | `MVCE-SHADOW-5M` / `MVCE-SHADOW-10M` / `MVCE-ISOCHRONE-{時間}H` |
| `MVE-NORTH` / `MVE-SUMMARY` / `MVE-RIDGE` | `MVCE-NORTH` / `MVCE-SUMMARY` / `MVCE-RIDGE` |

Python 版（`io/drawing.py`）とブラウザ版（`web/mvce/dxf.js`）を同時に
変えてあるので、parity は保たれます。R12 のレイヤ名制限（31文字以内・
大文字）にも収まっています（最長 `MVCE-ISOCHRONE-2_5H` で19文字）。

> **既存図面への影響** — 過去に MVCE / MVE が出した DXF を開いている
> JW-CAD 側のレイヤ設定は、新しい出力とレイヤ名が一致しなくなります。
> 線色・線種をレイヤごとに設定してあるテンプレートは、`MVCE-*` 向けに
> 設定し直しが要ります。互換のため旧名で出す設定は**用意していません**。
> 必要なら言ってください。

#### 2. `docs/legal_basis.md` ではなく `docs/mvce/legal_basis.md` に置いた

基本設計書 第3.2節のツリーは `docs/legal_basis.md` を指していますが、
このリポジトリの `docs/legal_basis.md` は旧 `jwcad_volume` パッケージの
ものとして既に存在します。MVCE の文書は `docs/mvce/` 配下にまとまって
いるので、そちらに置きました。`docs/mvce/profiles.md`（Phase 2）、
`docs/mvce/regression_notes.md`（Phase 2）も同じ場所に作る想定です。

#### 3. 不変条件 M-6 は `FAIL` に対しても効かせた

M-6 は「下位のどれか一つでも `UNDETERMINED` なら、上位の総合判定も
`UNDETERMINED`」と書いてあります。`FAIL` と `UNDETERMINED` が並んだとき
どちらが勝つかは書かれていませんが、条文どおり `UNDETERMINED` を勝たせ
ました。

理由は不変条件 M-3 です。MVCE の出力は「なぜこれ以上入らないか」
（`binding_constraint`）を答えられなければ事業収支の判断材料になりません。
判断できない制約が残っている限り支配的制約を名指しできないので、
総合判定は「判断できない」が正確です。

情報は落ちません。`Judgement.parts` に下位判定がそのまま残るので、
`judgement.find(Verdict.FAIL)` で明確な不適合を取り出せます。

「日影が明確に落ちているなら総合も `FAIL` にしてほしい」という運用なら、
`mvce/verdict.py` の `_PRECEDENCE` を1行変えるだけです。

#### 4. `Verdict.UNDETERMINED` には理由を必須にした

`Judgement` の生成時に、`UNDETERMINED` なのに `Reason` も下位判定も無い
場合は `VerdictError` にしています。原則H の「サイレントなデフォルト値
充填をしない」を、呼び出し側の心がけではなく型で担保するためです。

同じ考えで、`parts` を持つ `Judgement` の `verdict` が
`combine(parts)` と食い違う場合も生成時に落とします。集約する側が
`PASS` で握りつぶせません。

#### 5. `UNDETERMINED` 番兵は算術を拒否する

`achievable_far: float | UNDETERMINED`（第8.2節）のような数値フィールド
のために番兵オブジェクトを置きました。`0` や `NaN` として静かに計算へ
紛れ込むのを防ぐため、四則演算・比較・`float()` はすべて `TypeError` に
しています。`None`（未設定）とも区別します。

### 2026-08-30（3回目）— 施行令の斜線緩和がそろいました

**法52条9項が完全に解除されました。** 令135条の18 の算式は

#### V が効く場面

`Boundary.ground_level_diff_m` は「正の値で敷地の方が**低い**」と定義され、
道路・隣地・北側の3つの緩和が同じ向きで使っています。ところが条文は
道路だけ向きが逆です。

| 条文 | 緩和が効く条件 | フィールドの定義と |
|---|---|---|
| 令135条の2（道路） | 敷地が道路より1m以上**高い** | **合わない** |
| 令135条の3第1項2号（隣地） | 敷地が隣地より1m以上**低い** | 合う |
| 令135条の4第1項2号（北側） | 敷地が北側隣地より1m以上**低い** | 合う |

実測（1住居・容積率200%・幅員6m・敷地から5mの点）では、敷地が道路より
3m低いとき **13.75m → 14.75m** と、条文にない +1.0m が付いています。

直すには符号を変えるだけでは足りません。1つのフィールドで3つの緩和を
まかなっているので、道路と隣地で向きが違うことを表現できないためです。
**入力の互換性が壊れる**ので、こちらの判断では動かしていません。

### 2026-08-30（5回目）— 法52条9項（特定道路）

令135条の18 が揃ったので実装しました。`far.py` に

法52条2項の「幅員」は ①12m未満かの判定 ②前面道路が2以上あるときの最大の
選択 ③乗ずる数値の元、の3か所に出ます。読み替えはその**すべて**にかかる
ので、3つとも加算後の値で見ます。

- ②の結果、実幅員 東8m・南6m でも、南に加算3mが付けば南の 9m が最大に

### 2026-08-30（6回目）— 令2条2項（平均地盤面）

`mvce/ground.py` を新設しました。Phase 1 の残りの1つめです。

#### 接地線は「建物の輪郭」であって敷地境界線ではない

条文は「**建築物が**周囲の地面と接する位置の平均の高さ」です。同じ敷地でも
建物の置き方で地盤面が変わります。MVCE は建物の輪郭を探索の結果として
決めるので、地盤面を先に固定できません。

なので `ground.py` は**接地線（`ContactPoint` の並び）を受け取るだけ**に
しました。どの輪郭を使うかは呼び出し側の判断です。`Site.ground_contour()`
は「敷地境界いっぱいに建つ」と置いた接地線を返しますが、壁面後退を取る
計画では実際の接地線と違うことを docstring に書いてあります。

#### 条文が決めていない2点

**1. 「平均の高さ」の取り方** — 長さ加重平均を既定にしました。

条文は「平均の高さ」としか書いていません。頂点の単純平均か、接地線の
長さで重み付けした平均かで答えが変わります。実務は長さ加重（接地部分の
立面の断面積 ÷ 接地長）なので、これを既定にしました。**条文の文言では
なく解釈です。** `weighted=False` で単純平均に切り替えられます。

ここを `UNDETERMINED` にすると傾斜地が一切計算できなくなるので、通説を
既定にして「解釈である」と明示する側を選びました。定数ではなく引数に
してあるので、`ComplianceProfile` から差し替えられます。

長方形では両者が必ず一致します（どの頂点も長辺と短辺に1本ずつ挟まれる
ので重みが等しい）。差が出るのは長辺の途中に頂点があるときなどで、
テストはその形で書いてあります。

**2. 3m超のときの区分の切り方** — `UndeterminedRegulation` で止めます。

条文は「その高低差三メートル以内ごとの平均の高さ」としか書いておらず、
**どこで切るかを指定していません**。標高で切るのか建物を平面的に区切るのか
も書き分けられていません。令135条の7第3項の「高低差区分区域」は
「敷地を区分した区域」と平面的な区分を明示していて、書きぶりが違います。

切り方で答えが変わるので既定値では埋めません。呼び出し側が
`split_by_elevation()`（標高で切る読み方）か `ground_planes()`（区分済みの
接地線を直接渡す）で区分を決めたときだけ計算します。

`GroundPlaneSet.level_m` も、`multi` のときは単一の値を返さず例外にして
います。「どの地盤面で測るか」は部位ごとに決まるので、1つの数字で
答えると必ずどこかが嘘になります。

#### 3mの境界

条文は「三メートルを**超える**場合」なので、ちょうど3mは分けません。
テストで固定しました（`test_exactly_3m_is_still_one_plane`）。

#### まだ繋いでいないこと（大事）

**高さの判定はいまも Z=0 から測っています。** 地盤面を算定できるように
なっただけで、斜線・絶対高さ・日影の測定面をそこから測るところまでは
繋いでいません。半端に繋ぐと既存の `ground_level_diff_m`（令135条の2・
3・4の高低差緩和）と二重に効きかねないので、分けました。

ただし黙って無視するのが一番まずいので、`ground_levels` を与えた敷地では
最適化結果に注記を出します。

| 地盤の入力 | 注記 |
|---|---|
| なし | 出さない（平坦地なので差が無い） |
| 一様に +3m | 「一様なので相対的な結果は変わりません」 |
| 0/0/2/2 | 「平均地盤面 +1.000m。ただし高さの判定はまだ Z=0 から」 |
| 0/0/5/5 | 「地盤面が求まりません（3m超）。Z=0 を地盤面として判定」 |

### 2026-08-30（7回目）— 法52条7項・法53条2項（用途地域のまたがり）

#### まず対照表 — 同じ「またがり」でも条文ごとに扱いが違う

ここを取り違えると全部間違うので、モジュール docstring の頭に置きました。

| 規制 | 条文 | またがったときの扱い |
|---|---|---|
| 容積率 | 法52条7項 | **面積按分** |
| 建蔽率 | 法53条2項 | **面積按分** |

| 道路斜線 | 別表第三（い）欄 | **按分しない。**「建築物がある地域」ごと |
| 日影 | 令135条の13 | **按分しない。**各区域内にそれぞれ対象建築物があるものとして適用 |

法56条5項は今回はじめて条文にあたって確認しました。

> ５　建築物が第一項第二号及び第三号の地域、地区又は区域の二以上にわたる
> 場合においては、これらの規定中「建築物」とあるのは、「建築物の部分」と
> する。

#### 容積率の按分で一番間違えやすいところ

**係数が用途地域ごとに違う**ことです。前面道路の幅員は敷地に1つですが、
法52条2項の乗ずる数値は住居系 4/10、その他 6/10。だから
「指定容積率を按分してから道路幅員で切る」ではなく、**区域ごとに
`min(指定容積率, 幅員×係数)` を出してから按分**します。

前面道路6m、1住居200%（300m²）と近隣商業400%（300m²）が半々の敷地:

| 区域 | 指定 | 幅員×係数 | 限度 | 面積割合 | 寄与 |
|---|---|---|---|---|---|
| 1住居 | 200% | 6×0.4 = 240% | **200%** | 50% | 100% |
| 近隣商業 | 400% | 6×0.6 = 360% | **360%** | 50% | 180% |
| | | | | 合計 | **280%** |

先に按分すると 300% になって40%ぶん過大です。

法52条9項（特定道路）の読み替えは「第二項から第七項まで」なので、按分に
使う幅員も加算後の値です。テストで固定しました。

#### 面積の合計は黙って正規化しない

按分は「敷地面積に対する割合」なので、区分の面積の合計が敷地面積とずれて
いると按分そのものが狂います。正規化して進めると気づけないので、
`ZoneSplit.check_total_area()` がエラーにします。

#### 按分しない側は止める

用途地域が2以上あるとき、斜線・日影・絶対高さは
`require_single_zone_type()` が `UndeterminedRegulation` で止めます。

**片方の用途地域の値で計算すると、どちらに転ぶか分からない誤りになります。**
厳しい側とは限りません。いままでは `site.zoning` 1つしか無かったので、
そもそもまたがりを表現できず黙って片方で計算していました。表現できる
ようにした以上、黙って進めるのは今回いちばん避けたい形です。

結果として、`zone_split` を書くと容積率・建蔽率の按分はできますが
ボリューム探索はできません。これは機能の後退ではなく、いままで
出していた数字が信用できなかったことが見えるようになっただけです。

部分ごとの判定を入れるときの設計は決めて docstring に書いてあります:

- 点で答える関数（`height_limit_at` 等）は、その点がどの区域にあるかで
  `ZoningParams` を選ぶ（法56条5項の「建築物の部分」そのもの）
- 辺で答える関数（`required_setback_for_height`）は辺に沿って区域が
  変わりうるので、その辺が接する区域すべての最大値を取る（安全側）

`ZoneSplit` がいま面積しか持たず形を持たないのは、按分に面積割合しか
要らないからです。部分ごとの判定を入れるときに形を足します。

### やったこと — `mvce/crs.py`

基本設計書 4.6 の `CrsContext` を実装しました。あわせて `mvce/sources.py`
（`SourceRef`。原則F の出典必須フィールド）と、`north.resolve_north()`
を追加しています。

**1. 平面直角座標系は X が北・Y が東**

数学の慣習（x が東・y が北）と軸が逆です。EPSG の軸定義も測量成果も
X=北・Y=東 の順です。`CrsContext.to_local()` が取り込みの一点で必ず
入れ替えます。

入れ替え忘れは敷地が転置されるだけなので**面積は合ってしまい、斜線と
日影だけが静かに狂います**。テストで固定しました。

なお基本設計書 4.6 は「平面直角座標系の +Y 軸は『座標北』」と書いて
いますが、座標北は +X です。文意（座標北 ≠ 真北）はそのままで、
実装は EPSG の軸定義に合わせています。

**2. 子午線収差角**

Krüger 級数（6次）で順変換・逆変換・収差角・点縮尺を計算します。
純 Python で、実行時の外部依存はありません（L1 は純関数、基本設計 3.1）。

正しさは `tests/mvce/test_crs.py` が **pyproj** を独立実装として突き
合わせて担保します（不変条件 M-8 と同じ考え方）。pyproj は EPSG
データベースと PROJ の投影実装を同梱しているので、19系すべての原点
緯経度・縮尺係数・楕円体もそこから検証しています。

| 検証 | 許容差 |
|---|---|
| 投影座標（21点） | 1 µm |
| 子午線収差角（21点） | 1e-7 度 |
| 点縮尺（21点） | 1e-10 |
| 順逆の往復（21点・pyproj 不要） | 1e-9 度（≒0.1mm） |

さらに、収差角の**符号と大きさを幾何そのものから**確かめるテストを
入れました。同じ経度で緯度だけ上げた点は地球上では真北へ動くので、
その動きを平面座標で見た傾きが収差角に一致するはずです。式の出どころに
依存しない検証になります。

pyproj は `dev` extra です。入っていない環境では突合テストだけが skip
され、往復と幾何の自己検算（48件）は走ります。

**3. 真北の決定**

`north.resolve_north(crs, manual_north_angle_deg)` が真北を決めて、
**決めた根拠を注記で返します**。

- 座標系だけ → 収差角から計算
- 手入力だけ → そのまま採用
- 両方 → **手入力を優先**し、差を注記に出す（基本設計 4.6）。差が 0.1度
  を超えたら「真北記号が座標北を指している（収差角が未補正）か、系番号が
  違う可能性がある」と警告する
- どちらも無い → 0度にするが、**それが仮定であることを注記に出す**（原則H）

**4. 面積について**

平面直角座標系は k0 = 0.9999 の横メルカトル図法なので、図上面積は実面積と
最大 0.042% ほどずれます（600 m² の敷地で 0.25 m²）。建築確認で使う敷地面積は
登記・測量成果の値であってこの計算値ではないので、MVCE は図上面積を
そのまま使い、補正しません。必要なら `CrsContext.area_scale()` で倍率を
取れます。この判断は変えてよければ言ってください。

### 既存への影響

`Site` に `crs` フィールドが増えましたが、既定は `None` で、手描き図面
から起こした敷地の挙動は変わりません。既存テストは全件緑のままです。

## SITEINFO と MVCE の関係（2026-08-30）

SITEINFO は**敷地情報を入力するデータベースのカード**で、判定ロジックは
持ちません（定義は `statutes/README.md`）。入力項目が MVCE の `Site` と
ほぼ一致するので、対応を控えておきます。**SITEINFO が MvceRequest.site の
上流**になる、という理解です。

| SITEINFO の項目 | MVCE 側 | 状態 |
|---|---|---|
| 敷地の所在 | — | **MVCE に該当フィールドが無い** |
| 敷地のかたち（三斜 / ポリゴン / 座標 / GeoJSON） | `Site.points` ＋ `Site.crs` | 形式の対応は下記 |
| 方位 | `Site.north`（`north.resolve_north()`） | あり |
| 用途地域 | `ZoningParams.zone_type` | あり |
| 建蔽率 | `ZoningParams.coverage_ratio` | あり（緩和は未実装。食い違い M） |
| 容積率 | `ZoningParams.far_ratio` | あり |
| 前面道路幅員 | `Boundary.road_width_m`（辺ごと） | あり |
| 日影規制 | `ShadowRegulationSpec` | あり |
| 高さ規制 | `ZoningParams.absolute_height_limit_m` ＋ 高度地区 | 絶対高さのみ。**高度地区は Phase 1 で未実装** |

### 気づいた点3つ

**1. 敷地の所在を MVCE が持っていない**

基本設計書 8.1 の `MvceRequest` は `municipality_code`（全国地方公共団体
コード）を要求します。自治体 YAML（日影の規制時間・高度地区の勾配・
特定行政庁が定める係数）を引くのに要るからです。SITEINFO の「所在」から
それを導く経路が要ります。`Site` に住所フィールドを足すか、
`MvceRequest` 側で受けるかは Phase 4 の設計です。

**2. 敷地のかたちの入力形式**

MVCE の `io/` が読めるのは DXF・CSV・JSON です。SITEINFO の4形式との
対応は次のとおり。

| 形式 | MVCE 側 | 備考 |
|---|---|---|
| 座標 | `io/site_csv.py` / `io/site_json.py` | そのまま |
| ポリゴン | 同上 | そのまま |
| GeoJSON | **無い** | 下記の注意あり |
| 三斜（三斜求積） | **無い** | 三角形分割の求積表。頂点列への復元が要る |

**3. GeoJSON は原則D に触れる**

GeoJSON は既定で WGS84 の緯度経度です（RFC 7946）。原則D は
「WGS84 緯度経度での面積計算は禁止」なので、**取り込みの時点で
JGD2011 平面直角座標系へ変換**しなければなりません。

`crs.py` の `zone_for_epsg()` は EPSG:4326 と EPSG:6668（JGD2011 地理座標）を
明示的に弾いて「取り込み前に平面直角座標系へ変換してください」と言います。
その番人はすでに立っていますが、**変換そのものは未実装**です。
`crs.project()` は緯度経度 → 平面直角座標をやるので、JGD2011 の緯度経度
なら繋げます。WGS84 → JGD2011 の測地系変換（数メートルのずれ）は
別途必要です。

三斜と GeoJSON をいつ実装するかは、SITEINFO 側でどの形式を実際に使うかが
決まってからでよいと思います。

### 判断の記録

以下は基本設計書に明示がない、または書きぶりと現物がずれていた点について
実装側で下した判断です。**違うと思ったら差し替えてください。**

#### 1. DXF のレイヤ名 — Phase 0 では `MVE-*` を維持、2026-08-30 に `MVCE-*` へ変更

Phase 0 の時点では `MVE-SITE` などの既存レイヤ名をそのまま残しました。
受入基準が「挙動の変更ゼロ」であり、レイヤ名は JW-CAD 側のテンプレート・
線色設定・図面レイヤ分けが依存する出力仕様だからです。

**2026-08-30、直樹の判断で `MVCE-*` に切り替えました。** 基本設計書 7.1 が
`MVCE-ISOCHRONE-{時間}` と書いているのに合わせた形です。

| 旧 | 新 |
|---|---|
| `MVE-SITE` / `MVE-ROAD` / `MVE-SETBACK` / `MVE-OUTLINE` | `MVCE-SITE` / `MVCE-ROAD` / `MVCE-SETBACK` / `MVCE-OUTLINE` |
| `MVE-MESH` / `MVE-FLOORS` / `MVE-PLAN-n` | `MVCE-MESH` / `MVCE-FLOORS` / `MVCE-PLAN-n` |
| `MVE-SHADOW-5M` / `MVE-SHADOW-10M` / `MVE-ISOCHRONE-{時間}H` | `MVCE-SHADOW-5M` / `MVCE-SHADOW-10M` / `MVCE-ISOCHRONE-{時間}H` |
| `MVE-NORTH` / `MVE-SUMMARY` / `MVE-RIDGE` | `MVCE-NORTH` / `MVCE-SUMMARY` / `MVCE-RIDGE` |

Python 版（`io/drawing.py`）とブラウザ版（`web/mvce/dxf.js`）を同時に
変えてあるので、parity は保たれます。R12 のレイヤ名制限（31文字以内・
大文字）にも収まっています（最長 `MVCE-ISOCHRONE-2_5H` で19文字）。

> **既存図面への影響** — 過去に MVCE / MVE が出した DXF を開いている
> JW-CAD 側のレイヤ設定は、新しい出力とレイヤ名が一致しなくなります。
> 線色・線種をレイヤごとに設定してあるテンプレートは、`MVCE-*` 向けに
> 設定し直しが要ります。互換のため旧名で出す設定は**用意していません**。
> 必要なら言ってください。

#### 2. `docs/legal_basis.md` ではなく `docs/mvce/legal_basis.md` に置いた

基本設計書 第3.2節のツリーは `docs/legal_basis.md` を指していますが、
このリポジトリの `docs/legal_basis.md` は旧 `jwcad_volume` パッケージの
ものとして既に存在します。MVCE の文書は `docs/mvce/` 配下にまとまって
いるので、そちらに置きました。`docs/mvce/profiles.md`（Phase 2）、
`docs/mvce/regression_notes.md`（Phase 2）も同じ場所に作る想定です。

#### 3. 不変条件 M-6 は `FAIL` に対しても効かせた

M-6 は「下位のどれか一つでも `UNDETERMINED` なら、上位の総合判定も
`UNDETERMINED`」と書いてあります。`FAIL` と `UNDETERMINED` が並んだとき
どちらが勝つかは書かれていませんが、条文どおり `UNDETERMINED` を勝たせ
ました。

理由は不変条件 M-3 です。MVCE の出力は「なぜこれ以上入らないか」
（`binding_constraint`）を答えられなければ事業収支の判断材料になりません。
判断できない制約が残っている限り支配的制約を名指しできないので、
総合判定は「判断できない」が正確です。

情報は落ちません。`Judgement.parts` に下位判定がそのまま残るので、
`judgement.find(Verdict.FAIL)` で明確な不適合を取り出せます。

「日影が明確に落ちているなら総合も `FAIL` にしてほしい」という運用なら、
`mvce/verdict.py` の `_PRECEDENCE` を1行変えるだけです。

#### 4. `Verdict.UNDETERMINED` には理由を必須にした

`Judgement` の生成時に、`UNDETERMINED` なのに `Reason` も下位判定も無い
場合は `VerdictError` にしています。原則H の「サイレントなデフォルト値
充填をしない」を、呼び出し側の心がけではなく型で担保するためです。

同じ考えで、`parts` を持つ `Judgement` の `verdict` が
`combine(parts)` と食い違う場合も生成時に落とします。集約する側が
`PASS` で握りつぶせません。

#### 5. `UNDETERMINED` 番兵は算術を拒否する

`achievable_far: float | UNDETERMINED`（第8.2節）のような数値フィールド
のために番兵オブジェクトを置きました。`0` や `NaN` として静かに計算へ
紛れ込むのを防ぐため、四則演算・比較・`float()` はすべて `TypeError` に
しています。`None`（未設定）とも区別します。

### 止まっている理由 — e-Gov に到達できない（一部解決済み）

基本設計書 第0章の指示2は「第5章に列挙した条文番号・数値は、**実装前に
必ず e-Gov 法令検索の原文と照合**すること。この文書の数値を一次情報として
扱ってはならない」です。

この作業環境（Claude Code on the web のリモート実行環境）は、外向きの
通信がネットワークポリシーで絞られていて、法令の一次情報に到達できません。

```
laws.e-gov.go.jp   → CONNECT 403（ポリシー拒否）
elaws.e-gov.go.jp  → CONNECT 403
www.mlit.go.jp     → CONNECT 403
www.jcba-net.jp    → CONNECT 403
pypi.org           → 200（パッケージ取得は通る）
```

条文の原文が読めない以上、令2条2項の「3m」も、法52条9項の緩和式も、
令135条の12第2項の高低差の扱いも、**基本設計書に書かれた数値を写して
実装するしかありません**。それは第0章が明確に禁じていることです。

そこで Phase 1 のうち、**条文に依存しない `crs.py` だけを実装しました。**
残り5項目は条文照合ができる状態になってから着手します。

   環境設定は https://code.claude.com/docs/en/claude-code-on-the-web を

3. **ローカル環境（直樹の手元）で Phase 1 を回す。** この環境は
   e-Gov に出られないだけで、実装そのものは同じです。

2 が中長期には一番よさそうです。条文は改正されるので、「いつの版で実装
したか」がリポジトリに残るのは照合台帳の趣旨とも合います。

**→ 2026-08-30、2 の方式を採用しました。** `docs/mvce/statutes/` に条文を
置き、規約を `statutes/README.md` に書いています。なお現時点の収録分は
「直樹が e-Gov から転記して提供」であって機械的な取得ではないため、
その旨をメタデータに明記しています。転記ミスの余地があるので、重要な
数値を実装に落とす際はもう一度原文にあたるのが安全です。

### やったこと — `mvce/crs.py`

基本設計書 4.6 の `CrsContext` を実装しました。あわせて `mvce/sources.py`
（`SourceRef`。原則F の出典必須フィールド）と、`north.resolve_north()`
を追加しています。

**1. 平面直角座標系は X が北・Y が東**

数学の慣習（x が東・y が北）と軸が逆です。EPSG の軸定義も測量成果も
X=北・Y=東 の順です。`CrsContext.to_local()` が取り込みの一点で必ず
入れ替えます。

入れ替え忘れは敷地が転置されるだけなので**面積は合ってしまい、斜線と
日影だけが静かに狂います**。テストで固定しました。

なお基本設計書 4.6 は「平面直角座標系の +Y 軸は『座標北』」と書いて
いますが、座標北は +X です。文意（座標北 ≠ 真北）はそのままで、
実装は EPSG の軸定義に合わせています。

**2. 子午線収差角**

Krüger 級数（6次）で順変換・逆変換・収差角・点縮尺を計算します。
純 Python で、実行時の外部依存はありません（L1 は純関数、基本設計 3.1）。

正しさは `tests/mvce/test_crs.py` が **pyproj** を独立実装として突き
合わせて担保します（不変条件 M-8 と同じ考え方）。pyproj は EPSG
データベースと PROJ の投影実装を同梱しているので、19系すべての原点
緯経度・縮尺係数・楕円体もそこから検証しています。

| 検証 | 許容差 |
|---|---|
| 投影座標（21点） | 1 µm |
| 子午線収差角（21点） | 1e-7 度 |
| 点縮尺（21点） | 1e-10 |
| 順逆の往復（21点・pyproj 不要） | 1e-9 度（≒0.1mm） |

さらに、収差角の**符号と大きさを幾何そのものから**確かめるテストを
入れました。同じ経度で緯度だけ上げた点は地球上では真北へ動くので、
その動きを平面座標で見た傾きが収差角に一致するはずです。式の出どころに
依存しない検証になります。

pyproj は `dev` extra です。入っていない環境では突合テストだけが skip
され、往復と幾何の自己検算（48件）は走ります。

**3. 真北の決定**

`north.resolve_north(crs, manual_north_angle_deg)` が真北を決めて、
**決めた根拠を注記で返します**。

- 座標系だけ → 収差角から計算
- 手入力だけ → そのまま採用
- 両方 → **手入力を優先**し、差を注記に出す（基本設計 4.6）。差が 0.1度
  を超えたら「真北記号が座標北を指している（収差角が未補正）か、系番号が
  違う可能性がある」と警告する
- どちらも無い → 0度にするが、**それが仮定であることを注記に出す**（原則H）

**4. 面積について**

平面直角座標系は k0 = 0.9999 の横メルカトル図法なので、図上面積は実面積と
最大 0.042% ほどずれます（600 m² の敷地で 0.25 m²）。建築確認で使う敷地面積は
登記・測量成果の値であってこの計算値ではないので、MVCE は図上面積を
そのまま使い、補正しません。必要なら `CrsContext.area_scale()` で倍率を
取れます。この判断は変えてよければ言ってください。

### 既存への影響

`Site` に `crs` フィールドが増えましたが、既定は `None` で、手描き図面
から起こした敷地の挙動は変わりません。既存テストは全件緑のままです。

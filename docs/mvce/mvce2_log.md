### 判断の記録

以下は基本設計書に明示がない、または書きぶりと現物がずれていた点について
実装側で下した判断です。**違うと思ったら差し替えてください。**

#### 1. DXF のレイヤ名 — Phase 0 では `MVE-*` を維持、2026-08-30 に `MVCE-*` へ変更

Phase 0 の時点では `MVE-SITE` などの既存レイヤ名をそのまま残しました。
受入基準が「挙動の変更ゼロ」であり、レイヤ名は JW-CAD 側のテンプレート・
線色設定・図面レイヤ分けが依存する出力仕様だからです。

**2026-08-30、直樹の判断で `MVCE-*` に切り替えました。** 基本設計書 7.1 が
`MVCE-ISOCHRONE-{時間}` と書いているのに合わせた形です。

| 旧 | 新 |
|---|---|
| `MVE-SITE` / `MVE-ROAD` / `MVE-SETBACK` / `MVE-OUTLINE` | `MVCE-SITE` / `MVCE-ROAD` / `MVCE-SETBACK` / `MVCE-OUTLINE` |
| `MVE-MESH` / `MVE-FLOORS` / `MVE-PLAN-n` | `MVCE-MESH` / `MVCE-FLOORS` / `MVCE-PLAN-n` |
| `MVE-SHADOW-5M` / `MVE-SHADOW-10M` / `MVE-ISOCHRONE-{時間}H` | `MVCE-SHADOW-5M` / `MVCE-SHADOW-10M` / `MVCE-ISOCHRONE-{時間}H` |
| `MVE-NORTH` / `MVE-SUMMARY` / `MVE-RIDGE` | `MVCE-NORTH` / `MVCE-SUMMARY` / `MVCE-RIDGE` |

Python 版（`io/drawing.py`）とブラウザ版（`web/mvce/dxf.js`）を同時に
変えてあるので、parity は保たれます。R12 のレイヤ名制限（31文字以内・
大文字）にも収まっています（最長 `MVCE-ISOCHRONE-2_5H` で19文字）。

> **既存図面への影響** — 過去に MVCE / MVE が出した DXF を開いている
> JW-CAD 側のレイヤ設定は、新しい出力とレイヤ名が一致しなくなります。
> 線色・線種をレイヤごとに設定してあるテンプレートは、`MVCE-*` 向けに
> 設定し直しが要ります。互換のため旧名で出す設定は**用意していません**。
> 必要なら言ってください。

#### 2. `docs/legal_basis.md` ではなく `docs/mvce/legal_basis.md` に置いた

基本設計書 第3.2節のツリーは `docs/legal_basis.md` を指していますが、
このリポジトリの `docs/legal_basis.md` は旧 `jwcad_volume` パッケージの
ものとして既に存在します。MVCE の文書は `docs/mvce/` 配下にまとまって
いるので、そちらに置きました。`docs/mvce/profiles.md`（Phase 2）、
`docs/mvce/regression_notes.md`（Phase 2）も同じ場所に作る想定です。

#### 3. 不変条件 M-6 は `FAIL` に対しても効かせた

M-6 は「下位のどれか一つでも `UNDETERMINED` なら、上位の総合判定も
`UNDETERMINED`」と書いてあります。`FAIL` と `UNDETERMINED` が並んだとき
どちらが勝つかは書かれていませんが、条文どおり `UNDETERMINED` を勝たせ
ました。

理由は不変条件 M-3 です。MVCE の出力は「なぜこれ以上入らないか」
（`binding_constraint`）を答えられなければ事業収支の判断材料になりません。
判断できない制約が残っている限り支配的制約を名指しできないので、
総合判定は「判断できない」が正確です。

情報は落ちません。`Judgement.parts` に下位判定がそのまま残るので、
`judgement.find(Verdict.FAIL)` で明確な不適合を取り出せます。

「日影が明確に落ちているなら総合も `FAIL` にしてほしい」という運用なら、
`mvce/verdict.py` の `_PRECEDENCE` を1行変えるだけです。

#### 4. `Verdict.UNDETERMINED` には理由を必須にした

`Judgement` の生成時に、`UNDETERMINED` なのに `Reason` も下位判定も無い
場合は `VerdictError` にしています。原則H の「サイレントなデフォルト値
充填をしない」を、呼び出し側の心がけではなく型で担保するためです。

同じ考えで、`parts` を持つ `Judgement` の `verdict` が
`combine(parts)` と食い違う場合も生成時に落とします。集約する側が
`PASS` で握りつぶせません。

#### 5. `UNDETERMINED` 番兵は算術を拒否する

`achievable_far: float | UNDETERMINED`（第8.2節）のような数値フィールド
のために番兵オブジェクトを置きました。`0` や `NaN` として静かに計算へ
紛れ込むのを防ぐため、四則演算・比較・`float()` はすべて `TypeError` に
しています。`None`（未設定）とも区別します。

### 2026-08-30（3回目）— 施行令の斜線緩和がそろいました

**法52条9項が完全に解除されました。** 令135条の18 の算式は

#### V が効く場面

`Boundary.ground_level_diff_m` は「正の値で敷地の方が**低い**」と定義され、
道路・隣地・北側の3つの緩和が同じ向きで使っています。ところが条文は
道路だけ向きが逆です。

| 条文 | 緩和が効く条件 | フィールドの定義と |
|---|---|---|
| 令135条の2（道路） | 敷地が道路より1m以上**高い** | **合わない** |
| 令135条の3第1項2号（隣地） | 敷地が隣地より1m以上**低い** | 合う |
| 令135条の4第1項2号（北側） | 敷地が北側隣地より1m以上**低い** | 合う |

実測（1住居・容積率200%・幅員6m・敷地から5mの点）では、敷地が道路より
3m低いとき **13.75m → 14.75m** と、条文にない +1.0m が付いています。

直すには符号を変えるだけでは足りません。1つのフィールドで3つの緩和を
まかなっているので、道路と隣地で向きが違うことを表現できないためです。
**入力の互換性が壊れる**ので、こちらの判断では動かしていません。

### 2026-08-30（6回目）— 令2条2項（平均地盤面）

`mvce/ground.py` を新設しました。Phase 1 の残りの1つめです。

#### 接地線は「建物の輪郭」であって敷地境界線ではない

条文は「**建築物が**周囲の地面と接する位置の平均の高さ」です。同じ敷地でも
建物の置き方で地盤面が変わります。MVCE は建物の輪郭を探索の結果として
決めるので、地盤面を先に固定できません。

なので `ground.py` は**接地線（`ContactPoint` の並び）を受け取るだけ**に
しました。どの輪郭を使うかは呼び出し側の判断です。`Site.ground_contour()`
は「敷地境界いっぱいに建つ」と置いた接地線を返しますが、壁面後退を取る
計画では実際の接地線と違うことを docstring に書いてあります。

#### 条文が決めていない2点

**1. 「平均の高さ」の取り方** — 長さ加重平均を既定にしました。

条文は「平均の高さ」としか書いていません。頂点の単純平均か、接地線の
長さで重み付けした平均かで答えが変わります。実務は長さ加重（接地部分の
立面の断面積 ÷ 接地長）なので、これを既定にしました。**条文の文言では
なく解釈です。** `weighted=False` で単純平均に切り替えられます。

ここを `UNDETERMINED` にすると傾斜地が一切計算できなくなるので、通説を
既定にして「解釈である」と明示する側を選びました。定数ではなく引数に
してあるので、`ComplianceProfile` から差し替えられます。

長方形では両者が必ず一致します（どの頂点も長辺と短辺に1本ずつ挟まれる
ので重みが等しい）。差が出るのは長辺の途中に頂点があるときなどで、
テストはその形で書いてあります。

**2. 3m超のときの区分の切り方** — `UndeterminedRegulation` で止めます。

条文は「その高低差三メートル以内ごとの平均の高さ」としか書いておらず、
**どこで切るかを指定していません**。標高で切るのか建物を平面的に区切るのか
も書き分けられていません。令135条の7第3項の「高低差区分区域」は
「敷地を区分した区域」と平面的な区分を明示していて、書きぶりが違います。

切り方で答えが変わるので既定値では埋めません。呼び出し側が
`split_by_elevation()`（標高で切る読み方）か `ground_planes()`（区分済みの
接地線を直接渡す）で区分を決めたときだけ計算します。

`GroundPlaneSet.level_m` も、`multi` のときは単一の値を返さず例外にして
います。「どの地盤面で測るか」は部位ごとに決まるので、1つの数字で
答えると必ずどこかが嘘になります。

#### 3mの境界

条文は「三メートルを**超える**場合」なので、ちょうど3mは分けません。
テストで固定しました（`test_exactly_3m_is_still_one_plane`）。

#### まだ繋いでいないこと（大事）

**高さの判定はいまも Z=0 から測っています。** 地盤面を算定できるように
なっただけで、斜線・絶対高さ・日影の測定面をそこから測るところまでは
繋いでいません。半端に繋ぐと既存の `ground_level_diff_m`（令135条の2・
3・4の高低差緩和）と二重に効きかねないので、分けました。

ただし黙って無視するのが一番まずいので、`ground_levels` を与えた敷地では
最適化結果に注記を出します。

| 地盤の入力 | 注記 |
|---|---|
| なし | 出さない（平坦地なので差が無い） |
| 一様に +3m | 「一様なので相対的な結果は変わりません」 |
| 0/0/2/2 | 「平均地盤面 +1.000m。ただし高さの判定はまだ Z=0 から」 |
| 0/0/5/5 | 「地盤面が求まりません（3m超）。Z=0 を地盤面として判定」 |

### 2026-08-30（7回目）— 法52条7項・法53条2項（用途地域のまたがり）

`mvce/zone_split.py` を新設しました。Phase 1 の残りの2つめです。

#### まず対照表 — 同じ「またがり」でも条文ごとに扱いが違う

ここを取り違えると全部間違うので、モジュール docstring の頭に置きました。

| 規制 | 条文 | またがったときの扱い |
|---|---|---|
| 容積率 | 法52条7項 | **面積按分** |
| 建蔽率 | 法53条2項 | **面積按分** |
| 隣地・北側斜線 | 法56条5項 | **按分しない。**「建築物」→「建築物の部分」 |
| 道路斜線 | 別表第三（い）欄 | **按分しない。**「建築物がある地域」ごと |
| 日影 | 令135条の13 | **按分しない。**各区域内にそれぞれ対象建築物があるものとして適用 |

法56条5項は今回はじめて条文にあたって確認しました。

> ５　建築物が第一項第二号及び第三号の地域、地区又は区域の二以上にわたる
> 場合においては、これらの規定中「建築物」とあるのは、「建築物の部分」と
> する。

#### 容積率の按分で一番間違えやすいところ

**係数が用途地域ごとに違う**ことです。前面道路の幅員は敷地に1つですが、
法52条2項の乗ずる数値は住居系 4/10、その他 6/10。だから
「指定容積率を按分してから道路幅員で切る」ではなく、**区域ごとに
`min(指定容積率, 幅員×係数)` を出してから按分**します。

前面道路6m、1住居200%（300m²）と近隣商業400%（300m²）が半々の敷地:

| 区域 | 指定 | 幅員×係数 | 限度 | 面積割合 | 寄与 |
|---|---|---|---|---|---|
| 1住居 | 200% | 6×0.4 = 240% | **200%** | 50% | 100% |
| 近隣商業 | 400% | 6×0.6 = 360% | **360%** | 50% | 180% |
| | | | | 合計 | **280%** |

先に按分すると 300% になって40%ぶん過大です。

法52条9項（特定道路）の読み替えは「第二項から第七項まで」なので、按分に
使う幅員も加算後の値です。テストで固定しました。

#### 面積の合計は黙って正規化しない

按分は「敷地面積に対する割合」なので、区分の面積の合計が敷地面積とずれて
いると按分そのものが狂います。正規化して進めると気づけないので、
`ZoneSplit.check_total_area()` がエラーにします。

#### 按分しない側は止める

用途地域が2以上あるとき、斜線・日影・絶対高さは
`require_single_zone_type()` が `UndeterminedRegulation` で止めます。

**片方の用途地域の値で計算すると、どちらに転ぶか分からない誤りになります。**
厳しい側とは限りません。いままでは `site.zoning` 1つしか無かったので、
そもそもまたがりを表現できず黙って片方で計算していました。表現できる
ようにした以上、黙って進めるのは今回いちばん避けたい形です。

結果として、`zone_split` を書くと容積率・建蔽率の按分はできますが
ボリューム探索はできません。これは機能の後退ではなく、いままで
出していた数字が信用できなかったことが見えるようになっただけです。

部分ごとの判定を入れるときの設計は決めて docstring に書いてあります:

- 点で答える関数（`height_limit_at` 等）は、その点がどの区域にあるかで
  `ZoningParams` を選ぶ（法56条5項の「建築物の部分」そのもの）
- 辺で答える関数（`required_setback_for_height`）は辺に沿って区域が
  変わりうるので、その辺が接する区域すべての最大値を取る（安全側）

`ZoneSplit` がいま面積しか持たず形を持たないのは、按分に面積割合しか
要らないからです。部分ごとの判定を入れるときに形を足します。

#### ブラウザ版

`zone_split` と `ground_levels` を持つ YAML を読み込もうとしたら、
黙って無視せずエラーにしました。ブラウザ版は用途地域1つの前提のままです。

## Phase 2 — 天空率の告示準拠化

### 2026-08-30（10回目）— 算定位置（令135条の9・10・11）

Phase 2 の1つめ。**従来の実装で一番大きく条文とずれていたところ**です。

#### 何がずれていたか

| | 従来 | 条文 |
|---|---|---|
| 道路の基準線 | 前面道路の反対側の境界線 ✅ | 同じ |
| 隣地の基準線 | **境界線の上** ❌ | 境界線から **16m**（勾配1.25）/ **12.4m**（2.5）**外側** |
| 北側の基準線 | **境界線の上** ❌ | **真北方向**に **4m**（低層・田園）/ **8m**（中高層）外側 |
| 間隔 | **全部 2m** ❌ | 道路 幅員の1/2 / 隣地 8m・6.2m / 北側 1m・2m |
| 中心の高さ | **全部 0** ❌ | 道路は路面の中心、隣地・北側は敷地の地盤面（各条第4項の高低差みなし込み） |

基準線の距離は法56条7項各号、位置と間隔は令135条の9〜11 です。

**北側の低層住専は条文が1m以内なのに2mで刻んでいました。粗い側＝危険側**
です。測定点の間をすり抜ける形が通ってしまいます。

隣地が境界線の上だったのは、計画建築物も適合建築物も実際よりずっと近くから
見ていたということです。Ps と Pr の両方が変わるのでどちらに転ぶとは言え
ませんが、条文の位置ではありませんでした。

#### 北側の「真北方向」

令135条の11第1項1号は「真北に面する部分の両端**から真北方向の**基準線上の
位置」です。**垂線ではありません。** 真北が図面の上から振れている敷地では
別の点になります。基準線自体も「真北方向への水平距離が4m（8m）だけ外側の
線」＝辺を真北に平行移動した線なので、辺の端点を真北に4m送れば足ります。

#### 条文が書いていないので解釈したところ

**北側の基準線が前面道路のとき。** 法56条7項3号は「**隣地境界線**から真北
方向への水平距離が…」としか書いていません。しかし法56条1項3号は
「**前面道路の反対側の境界線又は**隣地境界線までの真北方向の水平距離」から
測ります。北側が前面道路の敷地で7項3号を動かすには反対側の境界線を起点に
するしかないので、そう読みました。台帳に記録してあります。

#### 間隔の指定は「細かくする方向」だけ

`sky_ratio_interval_m` は既定を **4.0 から「条文の間隔」に変えました**。
値を入れるとそこまで細かくできますが、条文より粗くはできません
（`min` を取ります）。粗いと測定点の間をすり抜けるので、粗くする自由は
あってはいけません。

#### 見つかったこと — 同時最適化は逐次より必ず良い、ではない

算定位置を条文に直したら、`test_interleaving_never_removes_more_than_sequential`
と `test_interleaving_can_beat_sequential_after_refill` が落ちました。

調べたところ、**「交互方式のほうが必ず多い」は成り立たない**ことが
分かりました。隣地の測定点が16m外側に離れて天空率の拘束がずっと弱くなり、
40m×25m・道路12m・容積率400% の条件では交互方式が 9m²（0.3%）**少なく**
なります。ほかの4条件では同点でした。

交互方式は「片方の是正がもう片方も満たしていた場合の削り込みの重複を
避ける」ヒューリスティックで、貪欲な選び方が違うので逐次方式に負ける
条件があります。**テストを通る条件に付け替えるのではなく、主張のほうを
実際に保証できることに直しました**（どちらも独立検証で適合する／差は数%
以内）。

#### まだ告示準拠ではないところ

- **天空図の投影方法** … 正射影（ρ = cos仰角）で方位を等分サンプリング。
  告示の作図方法そのものではありません
- **令135条の5 の Ab** … 「建築物**及びその敷地の地盤**」ですが、地盤の
  投影を見ていません（平坦地では寄与しない。食い違い J）
- **適合建築物（令135条の6・7・8）** … 階段室等・棟飾等の除外、
  勾配が異なる地域等ごと／令132条・令134条2項の区域ごと／高低差区分区域
  ごとの分割。次に着手します
- **令135条の9〜11 の各第5項** … 特定行政庁が規則で高さを別に定める場合。
  規則を入力する口がありません

### 2026-08-30（11回目）— 適合建築物（令135条の6・7・8）

Phase 2 の2つめ。**危険側の誤りが1つ見つかりました。**

#### 危険側だったもの — 階段状近似の向き

適合建築物は階段状のブロックで近似します。層の断面をどの高さで取るかで、
立体が真の包絡形より大きくなるか小さくなるかが決まります。

| 断面を取る高さ | 立体 | Pr | 判定 |
|---|---|---|---|
| 層の**下端** | 真の形を**含む**（大きい） | **小さい** | **甘い＝危険側** |
| 層の**上端** | 真の形に**含まれる**（小さい） | 大きい | 厳しい＝安全側 |

従来は下端で取っていて、コメントには「層の途中より大きめ＝天空を塞ぐ側に
安全」と書いてありました。**向きの評価が逆でした。** 塞ぐ側は Pr を下げる
ので、`Ps ≧ Pr` の基準が下がり、本来通らない計画が通ります。

上端に直しました。20層・頂部30mなら層厚1.5m、勾配1.25で水平方向のずれは
約1.2m。層を増やせば真の値に近づきます。

各ブロックの頂部がその平面のどこでも真の制限を超えないことを、3規制すべて
についてテストで固定しました。

#### 規制ごとに別の適合建築物

令135条の6は道路高さ制限だけ、令135条の7は隣地高さ制限だけ、令135条の8は
北側高さ制限だけに適合する形です。**3つを合成した1つの形ではありません。**

従来は合成した1つの形を、道路・隣地・北側のどの測定点でも Pr の元に
していました。合成した形は各規制単独より小さいので Pr は大きく出て、
判定としては厳しい側でしたが条文どおりではありません。

30m×20m・1種中高層・道路6m の敷地だと、頂部の高さはこうなります。

| 適合建築物 | 頂部 | 決めているもの |
|---|---|---|
| 道路（令135条の6） | 25.0m | 1.25 × 適用距離20m |
| 隣地（令135条の7） | 38.75m | 20 + 1.25 × 15m（敷地の奥行の半分） |
| 北側（令135条の8） | 35.0m | 10 + 1.25 × 20m（北辺から南端まで） |

#### 分けるときの落とし穴 — 適用距離で切らないと何でも通る

道路だけの適合建築物を素直に組むと、**適用距離の外側が「制限なし＝どこまでも
高い」形**になります。Pr が極端に小さく出て、何を建てても通ります。

令135条の6第1項1号が「道路高さ制限が適用される**範囲内の部分に限る**」と
しているので、別表第三（は）欄の適用距離までの帯で切り落とします。
これは省略できません。

同じ「限る」は**計画建築物にもかかります**。適合建築物だけ切って計画建築物を
丸ごと見ると比較になりません（範囲が空のとき Ps < Pr = 100% で必ず落ちる）。
両方切るようにしました。

商業・容積率600%・道路20m・後退5m の敷地では、適用距離25mを道路幅員と
後退距離で使い切って**範囲が敷地に届きません**。このとき道路高さ制限は
どこにもかからないので、両方が空になって 100% 対 100% で自動的に適合
します。切るのを片方だけにしていると、ここで必ず落ちていました。

#### `required_setback_for_height` は使えなかった

あれは「適用距離まで下がれば以降は自由」と頭打ちにします。ボリューム探索
には正しい扱いですが、適合建築物に使うと帯の中に何も残りません。
頭打ちにしない `slant_distance_for_height()` を `road_slant.py` に別に
置きました。

#### 前面道路が2以上なら止める

令135条の6第3項・令135条の9第3項が、前面道路が2以上ある場合に
**令132条・令134条2項の区域ごと**に適合建築物・算定位置・計画建築物を
切り分けて比較しろと定めています。MVCE は区域分割ができません。

近似して進めることも考えましたが、`UndeterminedRegulation` で止める
ことにしました。理由は2つです。

1. 区域分割をしない近似がどちら向きにずれるか、証明できません。3つの
   効果（適合建築物が小さくなる／測定点が増える／計画建築物を切らない）は
   いずれも厳しい側に見えますが、読みであって証明ではありません
2. 帯の和集合が非凸になり、ブラウザ版（半平面クリップしか持たない）で
   同じ形を作れません。Python と JS が食い違うほうが危険です

角地で天空率が使えなくなるのは痛いところです。**近似してでも通したい
場合は言ってください**（原則H に従って既定は止める側にしました）。

#### インデックスと多角形版の一致が崩れた

計画建築物を範囲で切るようになって、インデックス（マス単位でしか切れない）と
多角形版（平面形状を正確に切る）で Ps が変わりました。インデックスは範囲に
一部でもかかったマスを丸ごと残すので、**常に厳しい側**に出ます。

テストの主張を「厳密に一致」から「インデックスの余裕は多角形版を上回らない」
に直しました。この向きが崩れたら、最適化が「適合」と言った結果が実際には
不適合になりうるということです。

#### 3Dビューア

`viewer3d.py` が描いていた「baseline」は斜線制限すべてを合成した包絡形で、
適合建築物とは別物です。`slant_envelope()` として名前を分けました。

法55条1項は「**十メートル又は十二メートルのうち当該地域に関する都市計画に

推測で実装しません。どちらの読み方でも現行実装より厳しくなる方向なので、

### 2026-08-30（14回目）— 法56条1項3号の括弧書き（食い違い H）

資料待ちのあいだに、条文が明確なものをもう1つ。

#### 中高層住専に日影規制の指定があれば北側斜線はかからない

    三　第一種低層住居専用地域、第二種低層住居専用地域若しくは田園住居地域内
    又は第一種中高層住居専用地域若しくは第二種中高層住居専用地域（**次条
    第一項の規定に基づく条例で別表第四の二の項に規定する（一）、（二）又は
    （三）の号が指定されているものを除く。以下この号及び第七項第三号に
    おいて同じ。**）内においては、（略）

**括弧書きが付いているのは中高層住専だけ**です。低層住専・田園住居は
「又は」の前に列挙されていて括弧書きの外なので、指定があっても北側斜線は
残ります。ここを一括で外すと低層住専が緩くなるので、テストで両方向を
固定しました。

#### 「第七項第三号において同じ」を落とさない

括弧書きの末尾がこう言っているので、**天空率の北側の算定位置も無くなります**。
`sky_positions.north_positions()` が `north_slant.applies()` を見るように
しました。ここを落とすと、存在しない規制のために天空率を要求することに
なります。

#### 既定は False にしました

日影規制を計算するということは対象区域内にあるはずなので、自動で外すことも
考えました。やめた理由は、**対象区域外の中高層住専で日影を試算しただけの人**
にまで北側斜線が消えてしまうからです。日影規制の spec は `Site` の外にあり、
`north_slant.applies(site)` からは見えないという事情もあります。

代わりに、日影規制を計算しているのに指定が無い中高層住専では注記を出して、
「いまの結果は厳しい側です」と伝えます。黙って厳しくするのは、黙って
緩くするよりはましですが、気づけないのは同じなので。

#### M（建蔽率の緩和）は資料待ちに回しました

着手しようとしましたが、収録済みの法53条3項が**現行版ではありません**。
2号構成（防火地域内の耐火建築物／角地）で、現行は準防火地域と準耐火建築物を
含む3号構成です。archive のヘッダにも注記があります。現行版が要ります。

### 2026-08-30（15回目）— 令132条の区域区分（食い違い W の解消）

直樹が「新JCBA方式の解説」の PDF をアップロードしてくれたので、資料待ちが
1つ解けました。`docs/mvce/methods/` に収録し、`road_regions.py` を新設。

#### 何が分からなくて止めていたか

令132条2項・3項は「2以上の前面道路の到達範囲」で区域を切ります。前面道路が
3本以上あると、点ごとにどの道路の集合が前面道路になるかが変わる。その
切り方が条文だけでは読み切れず、`UndeterminedRegulation` で止めていました。

#### 資料で確認できたこと

**1項の 2A 区域を生むのは最大幅員の道路だけ。** 狭い道路側からは区分
しません。報告書がわざわざ「行わない」と書いていて、間違いが多いところ
だそうです。

**1項(b) は「その他の*すべての*前面道路の中心線から10m超」。** 従来の
2本用の実装は「その辺自身の中心線」しか見ていませんでした。2本なら
等価ですが、3本以上では違います。これは実装のバグでもありました。

#### 実装

到達範囲 `reach(W) = min(35, 2W)`（4m未満は `min(35, 10 − W/2)`）を各道路に
与えて、点がどの道路の到達範囲に入るか（集合 S）で切ります。

| 条件 | 項 | 前面道路 | みなし幅員 |
|---|---|---|---|
| 最大幅員 A の 2A かつ 35m 以内、**または**他の全前面道路の中心線から 10m 超 | 1項 | すべて | A |
| 1項の外で \|S\| ≥ 2 | 2項 | S | max(S の幅員) |
| 1項の外で \|S\| = 1 | 3項 | その1本 | その幅員 |

解説の3方向道路の例（A=8m / B=6m / C=4.5m）で、図と同じ3区域が出ます。

**多角形版と点ごと版を両方作りました。** 天空率は区域を図形として要り、
斜線は点ごとに何万回も呼ばれるので距離だけで判定したい。両者が一致する
ことをランダムな点で固定しています。ここがずれると斜線と天空率で答えが
食い違います。

#### 効果

- **前面道路3本以上の敷地が計算できるようになりました**（食い違い W）
- 1項(b) の「すべての他の道路」の取りこぼしが直りました
- ブラウザ版も同じ判定に揃えました（3本以上の throw を削除）

#### 残っている未決

解説の図1-6-1（4方道路）は、狭い道路 C が B・D の区域に作る「2C」の
小区域を**作るな**（B・D の区域と一体に扱え）と言っています。この実装は
条文どおり集合で切るので、その小区域を作ります。

分けること自体は厳しい側（算定位置が増え、区域ごとの適合建築物はその区域の
前面道路すべての最小）ですが、方式と食い違います。**JCBA 報告書の原典が
要ります。**

#### 次

天空率の per-区域 の適合建築物・算定位置（令135条の6第3項・令135条の9第3項）。
区域が図形として取れたので、あとはそれを `sky_ratio` / `sky_positions` に
通せば角地の天空率が動きます。

前回「条文の係り方が2通りに読めて決着しない」と書いて止めたところです。

- ロの地域（近隣商業・準工業・商業・工業・工業専用）… 後退距離の加算が
  外れる（**厳しくなる**）

商業・後退3mの敷地で 63.50m → 56.00m。勾配2.5 × 後退3m ぶんちょうどです。

#### 旧法で実装しなくてよかった

| | 旧（平成30年版） | 現行 |
|---|---|---|
| 3項1号 | 8/10地域**外**の防火地域内の**耐火建築物** | 防火地域（8/10地域を除く）内の**耐火建築物等** **又は**準防火地域内の**耐火建築物等・準耐火建築物等** |

| みなし | 6項（防火地域の内外） | **7項** ＋ **8項**（準防火地域とその他）を新設 |

**準防火地域と準耐火建築物等が緩和の対象に入ったのが一番大きい違い**です。
旧法のまま実装していたら、準防火地域の敷地で +1/10 を取り落としていました。
「現行版が要る」と言って止めておいてよかった例です。

#### 実装したもの

- 3項: 1号（防火・準防火＋耐火性能）または 2号（角地指定）で +1/10、両方で +2/10
- 6項1号: 8/10 の地域の防火地域内の耐火建築物等は**制限そのものが適用されない**
- 7項・8項: またがりのみなし（`fire_zone` に `fire_partial` /
  `quasi_fire_partial`）

#### 順番

3項は「**前二項の規定の適用については**」なので、**1項の数値に加算してから
2項で按分**します。逆にすると答えが変わります。1住居50%（角地指定あり）と
商業60%（指定なし）が半々なら、加算が先で 60%。テストで固定しました。

6項は「前各項の規定は…適用しない」なので、区域のどれかが該当したら按分せず
制限なしにします。

#### `None` と 1.0 は違う

6項1号の適用除外は `coverage_ratio_limit()` が `None` を返します。1.0
（＝敷地いっぱいまで建てられる）と数値としては同じ結果になりますが、
「制限が無い」と「制限が100%」は意味が違うので分けました。

#### 実装しないもの

4項・5項（許可で限度を超えられる）と 6項2号・3号（巡査派出所等／公園等の
中の建築物＋許可）。許可は個別判断、用途は敷地情報から判定できません。

### 2026-08-31（18回目）— 角地の天空率が動きました（令135条の6第3項）

直樹の回答で令132条の最後の未決が消え、区域を天空率に通しました。

#### まず、未決が1つ消えました

JCBA 報告書 2009 の図1-6-1（4方道路）は、狭い道路 C が B・D の区域に作る
「2C」の小区域を**作るな**（B・D と一体に扱え）と言っています。PDF の
日本語がラスタ化されていてキャプションが読めず、残っていた問いは
「その一体の区域で **C の斜線もかかるのか**」の1点でした。

**直樹の回答: 「C もかかる」。** これで `road_regions.py` はそのままで
正しいと確定しました。区域ごとの適合建築物はその区域の前面道路**すべて**の
最小なので、`min(B, C)` は区分の仕方に依りません。図1-6-1 の「一体処理」は
**区域図の描き方**の話で、制限の中身の話ではありませんでした。

#### 天空率に通しました

令135条の6第3項・令135条の9第3項は、前面道路が2以上ある場合に

    「限る。）」→「限る。）の第百三十二条…に規定する区域ごとの部分」

と読み替えます。つまり**区域ごとに3つ**を切り分けます。

| 何を | どこで |
|---|---|
| 適合建築物 | `sky_ratio.reference_building(site, "road", region=…)` |
| 算定位置 | `sky_positions.road_positions(site, regions=…)` |
| 計画建築物 | `sky_ratio.applicable_regions()` で切る |

3つのキーは `MeasurementPosition.group_key`（`"road#0"`, `"road#1"`, …）で
揃えます。**1つでもキーがずれると、その測定点が空の適合建築物と比べられて
何でも通ります**。揃っていることをテストで固定しました。

区域内の扱いは条文どおりです。

- 抱える前面道路 … 1項は**すべて**、2項は「これらの前面道路のみ」、
  3項は「その接する前面道路のみ」
- 幅員 … 区域のみなし幅員。斜線にも、適用距離の帯の奥行き
  （適用距離 − みなし幅員 − 後退等）にも効きます
- 緩和 … 令132条が読み替えるのは**幅員だけ**なので、辺ごとの緩和は
  そのまま効かせます

#### 間隔だけは実幅員で割ります（条文が明示していない選択）

令135条の9第1項2号は「当該前面道路の幅員の二分の一」としか書いていません。
区域内では幅員が読み替えられていますが、みなし幅員（＝実幅員以上）で割ると
間隔が**粗く**なり、測定点の間をすり抜けます。実幅員なら間隔は同じか
細かくなるだけなので、そちらを採りました。台帳（食い違い AD）に記録済みです。

#### 検証

区域ごとの適合建築物の上面が、**点ごとに独立実装した令132条の道路斜線**
（`road_slant.height_limit_at` → `region_at_point`）と乱数の点で一致する
ことを確認しました。多角形版と距離版という2つの独立経路の突き合わせです。
インデックス（最適化用）が多角形の計算より甘くならないことも固定しました。

#### 止めたところ

**令134条2項を選んだ敷地は `UndeterminedRegulation` です。** 令135条の6第3項は
「令132条**又は令134条2項**に規定する区域ごと」と言っていますが、MVCE の
令134条2項は点ごとの判定しか持たず、多角形の区域を作れません。近似すると
どちら向きにずれるか言えないので止めます（原則H）。`apply_article_134_2` を
外せば令132条1項によることになり、計算できます。

**ブラウザ版（JS）は従来どおり止まります。** 区域区分は多角形の差集合・
和集合が要りますが、JS 側は半平面クリップしか持ちません。止まる側なので
危険ではありませんが、Python 版との機能差です。

**方式ごとの違いも入っていません。** 東京都方式の入り隅の回り込みなどは
資料待ちで、`sky_region_split_method` は引き続き `None` 以外を拒否します。

### 止まっている理由 — e-Gov に到達できない（一部解決済み）

基本設計書 第0章の指示2は「第5章に列挙した条文番号・数値は、**実装前に
必ず e-Gov 法令検索の原文と照合**すること。この文書の数値を一次情報として
扱ってはならない」です。

この作業環境（Claude Code on the web のリモート実行環境）は、外向きの
通信がネットワークポリシーで絞られていて、法令の一次情報に到達できません。

```
laws.e-gov.go.jp   → CONNECT 403（ポリシー拒否）
elaws.e-gov.go.jp  → CONNECT 403
www.mlit.go.jp     → CONNECT 403
www.jcba-net.jp    → CONNECT 403
pypi.org           → 200（パッケージ取得は通る）
```

条文の原文が読めない以上、令2条2項の「3m」も、法52条9項の緩和式も、
令135条の12第2項の高低差の扱いも、**基本設計書に書かれた数値を写して
実装するしかありません**。それは第0章が明確に禁じていることです。

そこで Phase 1 のうち、**条文に依存しない `crs.py` だけを実装しました。**
残り5項目は条文照合ができる状態になってから着手します。

### 進めるための選択肢

1. **この環境の egress ポリシーに `laws.e-gov.go.jp` を追加する。**
   環境設定は https://code.claude.com/docs/en/claude-code-on-the-web を

2. **条文の原文をリポジトリに置く。** `docs/mvce/statutes/` に e-Gov から

   オフラインでも照合台帳が埋められ、改正の差分も git で追えます。
3. **ローカル環境（直樹の手元）で Phase 1 を回す。** この環境は
   e-Gov に出られないだけで、実装そのものは同じです。

2 が中長期には一番よさそうです。条文は改正されるので、「いつの版で実装
したか」がリポジトリに残るのは照合台帳の趣旨とも合います。

**→ 2026-08-30、2 の方式を採用しました。** `docs/mvce/statutes/` に条文を

### やったこと — `mvce/crs.py`

基本設計書 4.6 の `CrsContext` を実装しました。あわせて `mvce/sources.py`
（`SourceRef`。原則F の出典必須フィールド）と、`north.resolve_north()`
を追加しています。

**1. 平面直角座標系は X が北・Y が東**

数学の慣習（x が東・y が北）と軸が逆です。EPSG の軸定義も測量成果も
X=北・Y=東 の順です。`CrsContext.to_local()` が取り込みの一点で必ず
入れ替えます。

入れ替え忘れは敷地が転置されるだけなので**面積は合ってしまい、斜線と
日影だけが静かに狂います**。テストで固定しました。

なお基本設計書 4.6 は「平面直角座標系の +Y 軸は『座標北』」と書いて
いますが、座標北は +X です。文意（座標北 ≠ 真北）はそのままで、
実装は EPSG の軸定義に合わせています。

**2. 子午線収差角**

Krüger 級数（6次）で順変換・逆変換・収差角・点縮尺を計算します。
純 Python で、実行時の外部依存はありません（L1 は純関数、基本設計 3.1）。

正しさは `tests/mvce/test_crs.py` が **pyproj** を独立実装として突き
合わせて担保します（不変条件 M-8 と同じ考え方）。pyproj は EPSG
データベースと PROJ の投影実装を同梱しているので、19系すべての原点
緯経度・縮尺係数・楕円体もそこから検証しています。

| 検証 | 許容差 |
|---|---|
| 投影座標（21点） | 1 µm |
| 子午線収差角（21点） | 1e-7 度 |
| 点縮尺（21点） | 1e-10 |
| 順逆の往復（21点・pyproj 不要） | 1e-9 度（≒0.1mm） |

さらに、収差角の**符号と大きさを幾何そのものから**確かめるテストを
入れました。同じ経度で緯度だけ上げた点は地球上では真北へ動くので、
その動きを平面座標で見た傾きが収差角に一致するはずです。式の出どころに
依存しない検証になります。

pyproj は `dev` extra です。入っていない環境では突合テストだけが skip
され、往復と幾何の自己検算（48件）は走ります。

**3. 真北の決定**

`north.resolve_north(crs, manual_north_angle_deg)` が真北を決めて、
**決めた根拠を注記で返します**。

- 座標系だけ → 収差角から計算
- 手入力だけ → そのまま採用
- 両方 → **手入力を優先**し、差を注記に出す（基本設計 4.6）。差が 0.1度
  を超えたら「真北記号が座標北を指している（収差角が未補正）か、系番号が
  違う可能性がある」と警告する
- どちらも無い → 0度にするが、**それが仮定であることを注記に出す**（原則H）

**4. 面積について**

平面直角座標系は k0 = 0.9999 の横メルカトル図法なので、図上面積は実面積と
最大 0.042% ほどずれます（600 m² の敷地で 0.25 m²）。建築確認で使う敷地面積は
登記・測量成果の値であってこの計算値ではないので、MVCE は図上面積を
そのまま使い、補正しません。必要なら `CrsContext.area_scale()` で倍率を
取れます。この判断は変えてよければ言ってください。

### 既存への影響

`Site` に `crs` フィールドが増えましたが、既定は `None` で、手描き図面
から起こした敷地の挙動は変わりません。既存テストは全件緑のままです。

## SITEINFO と MVCE の関係（2026-08-30）

SITEINFO は**敷地情報を入力するデータベースのカード**で、判定ロジックは
持ちません（定義は `statutes/README.md`）。入力項目が MVCE の `Site` と
ほぼ一致するので、対応を控えておきます。**SITEINFO が MvceRequest.site の
上流**になる、という理解です。

| SITEINFO の項目 | MVCE 側 | 状態 |
|---|---|---|
| 敷地の所在 | — | **MVCE に該当フィールドが無い** |
| 敷地のかたち（三斜 / ポリゴン / 座標 / GeoJSON） | `Site.points` ＋ `Site.crs` | 形式の対応は下記 |
| 方位 | `Site.north`（`north.resolve_north()`） | あり |
| 用途地域 | `ZoningParams.zone_type` | あり |
| 建蔽率 | `ZoningParams.coverage_ratio` | あり（緩和は未実装。食い違い M） |
| 容積率 | `ZoningParams.far_ratio` | あり |
| 前面道路幅員 | `Boundary.road_width_m`（辺ごと） | あり |
| 日影規制 | `ShadowRegulationSpec` | あり |
| 高さ規制 | `ZoningParams.absolute_height_limit_m` ＋ 高度地区 | 絶対高さのみ。**高度地区は Phase 1 で未実装** |

### 気づいた点3つ

**1. 敷地の所在を MVCE が持っていない**

基本設計書 8.1 の `MvceRequest` は `municipality_code`（全国地方公共団体
コード）を要求します。自治体 YAML（日影の規制時間・高度地区の勾配・
特定行政庁が定める係数）を引くのに要るからです。SITEINFO の「所在」から
それを導く経路が要ります。`Site` に住所フィールドを足すか、
`MvceRequest` 側で受けるかは Phase 4 の設計です。

**2. 敷地のかたちの入力形式**

MVCE の `io/` が読めるのは DXF・CSV・JSON です。SITEINFO の4形式との
対応は次のとおり。

| 形式 | MVCE 側 | 備考 |
|---|---|---|
| 座標 | `io/site_csv.py` / `io/site_json.py` | そのまま |
| ポリゴン | 同上 | そのまま |
| GeoJSON | **無い** | 下記の注意あり |
| 三斜（三斜求積） | **無い** | 三角形分割の求積表。頂点列への復元が要る |

**3. GeoJSON は原則D に触れる**

GeoJSON は既定で WGS84 の緯度経度です（RFC 7946）。原則D は
「WGS84 緯度経度での面積計算は禁止」なので、**取り込みの時点で
JGD2011 平面直角座標系へ変換**しなければなりません。

`crs.py` の `zone_for_epsg()` は EPSG:4326 と EPSG:6668（JGD2011 地理座標）を
明示的に弾いて「取り込み前に平面直角座標系へ変換してください」と言います。
その番人はすでに立っていますが、**変換そのものは未実装**です。
`crs.project()` は緯度経度 → 平面直角座標をやるので、JGD2011 の緯度経度
なら繋げます。WGS84 → JGD2011 の測地系変換（数メートルのずれ）は
別途必要です。

三斜と GeoJSON をいつ実装するかは、SITEINFO 側でどの形式を実際に使うかが
決まってからでよいと思います。
